is operational evidence, not a claim that the intentionally ephemeral demo
environment remains online.

## Production defects found and corrected

The live deployment exposed five integration defects that repository-only
validation could not reproduce:

1. Kubernetes could not verify the distroless image's named `nonroot` user.
   Commit `5a18c84` pins UID and GID `65532` while preserving
   `runAsNonRoot` and the read-only root filesystem.
2. OpenTelemetry SDK default resources and a hard-coded semantic-convention
   schema conflicted at process startup. Commit `44f26e8` uses schemaless
   service attributes and adds a regression test.
3. Hardened Nginx required writable runtime scratch space. Commit `1595fce`
   mounts a size-limited, memory-backed `/tmp` while keeping the root
   filesystem read-only.
4. The lightweight OTel Kubernetes distribution lacked the configured
   Prometheus exporter. Commit `d16d656` moves the gateway to the official
   contrib distribution; both replicas then reported ready pipelines.
5. VPC CNI had NetworkPolicy support disabled, and the API egress rule targeted
   the VPC instead of the in-cluster API Service. Terraform now enables the
   native policy agent and the chart restricts API traffic to
   `172.20.0.1/32`. Controller-owned positive and negative test Jobs verified
   that intended traffic succeeds while untrusted traffic is blocked.

CI passed for each corrective commit. The final platform run was
[`33454660572`](https://github.com/andy98w/Kubernetes-Dashboard/actions/runs/33454660572).

## Load and recovery evidence

Fortio exercised the API for 30 seconds at 25 requests per second with eight
connections. All `744/744` requests returned HTTP 200; average latency was
`0.842 ms` and p99 was approximately `4.85 ms`.

Two controlled pod-loss tests ran while Fortio generated 20 requests per
second for 45 seconds:

- API: the replacement became Ready in 2 seconds; `896/896` requests returned
  HTTP 200, average latency was `0.741 ms`, and p99 was approximately `2.78 ms`.
- Web: the replacement became Ready in 2 seconds; `896/896` requests returned
  HTTP 200, average latency was `2.597 ms`, and p99 was approximately `8.51 ms`.

These results demonstrate request continuity for a single-pod disruption; they
are not a capacity limit or a substitute for a longer soak test.

## Security and policy assertions

- The API service account could list pods, as required by the read-only
  dashboard, but could not create Deployments or delete Secrets.
- The web service account could not read pods and does not mount a service
  account token.
- Both released images were deployed by immutable digest. API ran as numeric
  UID/GID `65532`; web ran as UID/GID `101`. Both used RuntimeDefault seccomp,
  dropped all capabilities, disallowed privilege escalation, and retained a
  read-only root filesystem.
- The EKS public endpoint allowed only the operator's current `/32`, with
  private endpoint access also enabled.
- VPC CNI reported `enableNetworkPolicy=true`; both `aws-node` DaemonSet pods
  ran the `aws-eks-nodeagent` policy container with zero restarts.
- A labeled smoke-test Job reached both services. A controller-owned untrusted
  Job timed out against both services and completed only after confirming both
  paths were blocked.
- `ClusterSecretStore/aws-secrets-manager` reported `Ready=True` and `Valid`.

Grafana's persisted SQLite administrator password had diverged from its
Kubernetes Secret after reconciliation. The persisted password was reset to
the Secret value and `/api/user` then returned HTTP 200 using Basic Auth; no
credential is recorded in this repository.

## Authenticated public delivery

The `kubevista.illuma.me` subdomain was delegated from Vercel DNS to a dedicated
Route53 hosted zone without changing the existing apex or `www` site. ACM
issued a DNS-validated certificate after an explicit subdomain CAA record
authorized Amazon's certificate authority. The validation CNAME is retained
for renewal.

ExternalDNS receives zone-scoped Route53 permissions through EKS Pod Identity.
The public ALB redirects HTTP to HTTPS and requires Cognito authorization before
forwarding. Cognito is configured for administrator-created accounts, strong
passwords, one-hour ALB sessions, and mandatory software-token MFA. The web
NetworkPolicy accepts ALB traffic from only the three public subnet CIDRs.
